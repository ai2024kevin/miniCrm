# Дизайн: автоматический роутинг между OpenAI-аккаунтами в GSD

## Контекст

В текущей конфигурации GSD OpenAI-аутентификация хранится в `C:\Users\Kerry\.gsd\agent\auth.json` как одиночный провайдер. Пользователь работает с несколькими купленными аккаунтами ChatGPT Plus, у которых есть пятичасовые и недельные лимиты. Цель этой работы — спроектировать внутренний механизм GSD, который автоматически переключает OpenAI-вызовы на следующий доступный аккаунт, когда текущий аккаунт исчерпал лимит.

Важно сохранить текущую модель работы GSD как локального инструмента, не превращая первую версию в универсальный мультипровайдерный оркестратор. При этом решение должно быть расширяемым и диагностируемым.

## Цель

Построить внутри GSD единый слой маршрутизации для всех OpenAI-вызовов, который:

- использует пул OpenAI-аккаунтов из одного `auth.json`;
- выбирает аккаунт по приоритетному списку;
- автоматически делает failover на следующий аккаунт при исчерпании лимита;
- сохраняет состояние недоступности аккаунтов между перезапусками;
- показывает пользователю понятную диагностику и текущий статус пула в GSD.

## Подтверждённые решения

- Область действия: все OpenAI-вызовы внутри GSD, а не только `openai-codex`.
- Триггер переключения для первой версии: ошибки лимита плюс ручное отключение аккаунта.
- Хранение нескольких аккаунтов: один `auth.json` с пулом OpenAI-аккаунтов.
- Основная стратегия выбора: `priority list`.
- После исчерпания лимита аккаунт не используется в пределах текущего окна, затем снова рассматривается в следующем цикле.
- Определение причины переключения: по коду/тексту ошибки и локальной классификации внутри GSD.
- Если все аккаунты недоступны, вызывающий код получает подробную диагностику по каждому аккаунту.
- Между перезапусками сохраняется состояние недоступности аккаунтов, но не полный аудит маршрутизации.
- Управление конфигурацией остаётся в `auth.json`, а GSD показывает простую статусную панель.
- Для конкурентных запросов нужен локальный `mutex` и защита от штормового многократного переключения.
- Аккаунт может автоматически вернуться в пул после локально известного окончания окна блокировки.
- Различие между пятичасовым и недельным лимитом должно быть видно в диагностике, но не должно усложнять публичную конфигурацию.

## Архитектура

### 1. AccountRegistry

`AccountRegistry` отвечает за чтение и валидацию OpenAI-пула из `C:\Users\Kerry\.gsd\agent\auth.json`.

Он должен:

- читать конфигурацию OpenAI-аккаунтов;
- валидировать обязательные поля;
- нормализовать структуру аккаунтов;
- возвращать аккаунты в порядке приоритета.

Он не должен:

- принимать runtime-решения;
- хранить доступность аккаунтов;
- модифицировать состояние failover.

Это отделяет статическую конфигурацию от оперативного состояния и не перегружает `auth.json` transient-данными.

### 2. RoutingStateStore

`RoutingStateStore` отвечает за хранение оперативного состояния аккаунтов между перезапусками GSD.

Он хранит:

- текущий статус доступности аккаунта;
- причину последней блокировки;
- время `lastFailureAt` как момент, когда аккаунт стал недоступен;
- время `blockedUntil` как уже вычисленную границу конца окна блокировки;
- время последней ошибки;
- время последнего успешного использования;
- последнее событие переключения в кратком виде.

Он не хранит:

- токены;
- refresh/access credentials;
- статическую конфигурацию аккаунтов.

### 3. OpenAIRouter

`OpenAIRouter` — единая точка входа для всех OpenAI-вызовов внутри GSD.

Он должен:

- выбрать первый доступный аккаунт по `priority list`;
- выполнить запрос через него;
- классифицировать ошибки;
- при необходимости исключить аккаунт из пула до конца окна;
- переключиться на следующий доступный аккаунт;
- вернуть либо успешный ответ, либо структурированную диагностику.

Ключевое архитектурное правило: остальной код GSD не должен вызывать OpenAI напрямую, минуя `OpenAIRouter`.

### 4. RoutingStatusView

`RoutingStatusView` — простая диагностическая панель в GSD.

Она должна показывать:

- текущий активный аккаунт;
- список аккаунтов в порядке приоритета;
- доступность каждого аккаунта;
- причину блокировки;
- время ожидаемого возврата в пул;
- последнее переключение: откуда, куда и почему.

Она не должна:

- редактировать `auth.json`;
- хранить собственную логику маршрутизации;
- показывать секреты.

## Модель данных

### Конфигурация: `auth.json`

`C:\Users\Kerry\.gsd\agent\auth.json` остаётся источником истины для конфигурации пула OpenAI-аккаунтов. Внутри него должна появиться секция вроде `openai_pool` с полем `accounts`.

Каждый аккаунт должен иметь стабильный `id`, чтобы runtime-state ссылался на аккаунт не по позиции в массиве, а по устойчивому идентификатору.

Логическая структура:

```json
{
  "openai_pool": {
    "strategy": "priority_list",
    "accounts": [
      {
        "id": "openai-main",
        "label": "Main Plus",
        "enabled": true,
        "priority": 100,
        "type": "oauth",
        "access": "...",
        "refresh": "...",
        "expires": 1776987766828,
        "accountId": "..."
      },
      {
        "id": "openai-backup-1",
        "label": "Backup 1",
        "enabled": true,
        "priority": 90,
        "type": "oauth",
        "access": "...",
        "refresh": "...",
        "expires": 1776987766828,
        "accountId": "..."
      }
    ]
  }
}
```

Эта часть отвечает только на вопрос: какие аккаунты существуют, включены ли они и в каком порядке должны рассматриваться.

### Runtime-state: `openai-routing-state.json`

Оперативное состояние должно храниться отдельно, например в файле:

`C:\Users\Kerry\.gsd\agent\openai-routing-state.json`

Логическая структура:

```json
{
  "version": 1,
  "accounts": {
    "openai-main": {
      "status": "blocked_quota_window",
      "blockedUntil": 1776150000000,
      "lastFailureReason": "quota_exhausted_5h",
      "lastFailureAt": 1776132000000,
      "lastSuccessAt": 1776128000000
    },
    "openai-backup-1": {
      "status": "available",
      "blockedUntil": null,
      "lastFailureReason": null,
      "lastFailureAt": null,
      "lastSuccessAt": 1776132100000
    }
  },
  "lastRoutingEvent": {
    "at": 1776132100000,
    "fromAccountId": "openai-main",
    "toAccountId": "openai-backup-1",
    "reason": "quota_exhausted_5h"
  }
}
```

Принципиальное требование: runtime-state не должен записываться обратно в `auth.json`, чтобы не смешивать секреты, конфигурацию и часто меняющееся состояние.

Для временной блокировки аккаунта поля `lastFailureAt` и `blockedUntil` являются обязательными persisted-полями. Это нужно, чтобы после перезапуска GSD система не теряла момент наступления недоступности и не возвращала аккаунт в пул раньше времени.

## Алгоритм маршрутизации

Для каждого OpenAI-запроса `OpenAIRouter` выполняет следующий порядок действий:

1. Читает пул аккаунтов из `AccountRegistry`.
2. Читает runtime-state из `RoutingStateStore`.
3. Отбрасывает аккаунты, которые:
   - отключены в конфиге;
   - вручную заблокированы;
   - временно заблокированы до `blockedUntil > now`;
   - имеют состояние `auth_invalid`.
4. Сортирует оставшиеся аккаунты по приоритету.
5. Берёт первый доступный аккаунт.
6. Выполняет запрос через него.

Если запрос проходит успешно:

- фиксируется `lastSuccessAt`;
- аккаунт остаётся доступным;
- ранее истёкшая временная блокировка считается автоматически завершённой.

Если запрос падает:

- ошибка прогоняется через локальный классификатор;
- по результату классификации обновляется runtime-state;
- если ошибка означает исчерпание лимита, аккаунт исключается из пула до конца локально известного окна;
- роутер делает failover на следующий доступный аккаунт.

Если доступных аккаунтов больше нет:

- возвращается структурированная ошибка пула, а не голая строка или бесконечный retry.

## Классификация ошибок

### Нормализованные причины уровня аккаунта

- `quota_exhausted`
- `quota_exhausted_5h`
- `quota_exhausted_weekly`
- `auth_invalid`
- `rate_limited`
- `network_error`
- `server_error`
- `unknown_error`

### Итоговые ошибки уровня роутера

- `openai_pool_exhausted`
- `openai_no_enabled_accounts`
- `openai_auth_config_invalid`
- `openai_router_internal_error`

Роутер принимает решения не по сырому тексту ошибки OpenAI, а по нормализованной локальной классификации. Это делает поведение устойчивее к вариациям provider-specific сообщений.

### Правила реакции на ошибки

- `quota_exhausted_*`: аккаунт блокируется до локально известного конца окна.
- `auth_invalid`: аккаунт исключается до ручного исправления auth.
- `rate_limited`: может давать мягкую временную блокировку, но не считается исчерпанием всего окна по умолчанию.
- `network_error` и `server_error`: не должны навсегда исключать аккаунт из пула.
- `unknown_error`: не должен автоматически переводить аккаунт в долгую блокировку без дополнительных оснований.

Если ошибка переводит аккаунт во временную недоступность, роутер обязан сохранить оба значения: `lastFailureAt` и уже вычисленный `blockedUntil`. Одного времени ошибки недостаточно, потому что после перезапуска система должна продолжать действовать от сохранённой границы окна, а не пытаться угадывать её заново.

Пятичасовой и недельный лимиты должны различаться в диагностике, но наружу по-прежнему представляться через общий механизм `blockedUntil`.

## Восстановление аккаунтов

В первой версии восстановление должно быть ленивым и автоматическим.

Правило:

- если `blockedUntil <= now`, аккаунт снова становится кандидатом на выбор;
- отдельный фоновый процесс разблокировки не требуется;
- восстановление происходит при следующем запросе и при чтении статуса для UI.

После перезапуска GSD восстановление также опирается на сохранённый `blockedUntil`, а не на пересчёт от текущего момента. Это исключает преждевременное возвращение аккаунта в пул.

Это упрощает систему и не требует лишней фоновой координации.

## Параллелизм и защита от штормового переключения

Для конкурентных запросов требуется локальная синхронизация.

Нужны три механизма:

1. `router mutex`
   Защищает выбор активного аккаунта и запись нового состояния.

2. `single switch decision`
   Если один поток уже пометил аккаунт как exhausted и переключился, остальные потоки должны увидеть обновлённый state и не делать повторное решение заново.

3. `reason deduplication`
   При серии одинаковых quota-ошибок состояние не должно многократно перезаписываться без необходимости.

Итоговая цель: избежать гонок, дребезга state и каскадного повторного failover на одних и тех же условиях.

## Диагностика и UI

### Что должна возвращать система при полном отказе пула

Если все аккаунты недоступны, верхний уровень GSD должен получить структурированную диагностику, которая содержит:

- итоговый `code`;
- человекочитаемое `message`;
- список `attemptedAccounts`;
- массив `accountDiagnostics`.

Для каждого аккаунта полезны поля:

- `accountId`
- `label`
- `priority`
- `status`
- `lastFailureReason`
- `blockedUntil`
- `wasTriedInThisRequest`
- `failureSource`

Это позволит UI показывать состояние без парсинга сырых логов и без знания низкоуровневых деталей OpenAI-клиента.

### Что должна показывать статусная панель

Минимально полезный набор:

- активный аккаунт сейчас;
- список аккаунтов в порядке приоритета;
- доступен ли аккаунт;
- причина недоступности;
- до какого времени действует блокировка;
- последний успешно использованный аккаунт;
- последнее событие переключения.

Если весь пул недоступен, панель должна ясно показать:

- что именно сломалось;
- какие аккаунты вернутся автоматически позже;
- какие аккаунты требуют ручного re-auth.

### Что нельзя показывать

В UI и логах нельзя показывать:

- access token;
- refresh token;
- сырой auth-объект;
- секреты из `auth.json`;
- полные provider payloads, если они содержат чувствительные данные.

## Тестирование

### AccountRegistry

Нужно проверить:

- корректный разбор нового формата `auth.json`;
- сортировку по приоритету;
- игнорирование отключённых аккаунтов;
- ошибки валидации при битом конфиге;
- устойчивость `id` и обработку дубликатов.

### RoutingStateStore

Нужно проверить:

- чтение и запись state-файла;
- восстановление состояния после перезапуска;
- поведение при отсутствии файла;
- поведение при частично повреждённом файле;
- обновление `blockedUntil`, `lastFailureReason`, `lastSuccessAt`.

### OpenAIRouter

Нужно проверить:

- выбор первого доступного аккаунта;
- failover при `quota_exhausted`;
- исключение `auth_invalid` из пула;
- корректный отказ, когда пул пуст;
- возврат аккаунта в пул после `blockedUntil`;
- отсутствие повторного выбора уже заблокированного аккаунта;
- корректную работу при конкурентных запросах.

### RoutingStatusView

Нужно проверить:

- корректное отображение состояния;
- понятную диагностику для полного отказа пула;
- отсутствие утечки секретов в UI и ошибках.

## Обязательные сценарии первой версии

- Один аккаунт доступен, запрос проходит успешно.
- Первый аккаунт исчерпан, второй подхватывает запрос.
- Первый аккаунт исчерпан и остаётся заблокирован до конца окна.
- После истечения окна первый аккаунт снова становится кандидатом.
- Один аккаунт требует re-auth, остальные продолжают работать.
- Все аккаунты недоступны, пользователь получает структурированную диагностику.
- Два параллельных запроса одновременно сталкиваются с exhausted-аккаунтом и не ломают state.

## Явно вне первой версии

Чтобы не размывать scope, первая версия не включает:

- балансировку нагрузки между аккаунтами;
- мультипровайдерный роутинг;
- автоматическое восстановление `auth_invalid`;
- очередь запросов и отложенные повторы;
- сложную аналитику usage;
- UI-редактирование аккаунтов прямо из GSD;
- фоновый health-checker;
- штрафные модели и рейтинги качества аккаунтов.

## Итог

Рекомендуемая реализация для GSD:

- один `auth.json` как конфигурация пула OpenAI-аккаунтов;
- отдельный `openai-routing-state.json` как источник runtime-state;
- четыре основных компонента: `AccountRegistry`, `RoutingStateStore`, `OpenAIRouter`, `RoutingStatusView`;
- политика выбора `priority list`;
- автоматический failover при исчерпании лимита;
- ленивое автовосстановление после конца окна;
- локальный `mutex` и anti-storm protection;
- подробная диагностика вместо молчаливой деградации.

Этот дизайн закрывает текущую практическую задачу пользователя и остаётся достаточно компактным для первой внедряемой версии в GSD.
